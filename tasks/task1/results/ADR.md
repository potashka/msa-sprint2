# ADR: Миграция Hotelio от Java-монолита к микросервисам

## Status: Proposed

## Context

Hotelio сейчас реализован как Java Spring Boot монолит с общей базой PostgreSQL. Основные модули приложения: `BookingService`, `UserService`, `HotelService`, `PromoCodeService`, `ReviewService`.

`BookingService` является точкой оркестрации создания бронирования: проверяет пользователя, отель, промокод и отзывы, рассчитывает итоговую цену и сохраняет бронирование в PostgreSQL. Сейчас эти зависимости являются внутрипроцессными вызовами внутри одного деплоя и одной базы данных.

Бизнес хочет мигрировать постепенно по паттерну Strangler Fig: выносить отдельные возможности во внешние сервисы, сохраняя остальную функциональность в монолите до ее миграции.

## Текущие проблемы архитектуры

- Монолит сложно безопасно изменять: логика бронирований, пользователей, отелей, промокодов и отзывов связана в одном коде и одном релизном цикле.
- Нельзя масштабировать бронирования независимо от менее нагруженных доменов.
- Ошибка в критичном сценарии бронирования может повлиять на все приложение, потому что все модули работают в одном runtime.
- Общая PostgreSQL схема размывает владение данными и мешает независимому развитию доменов.
- Фронтенд напрямую зависит от REST API монолита, поэтому нет BFF/Gateway слоя для постепенного роутинга и композиции клиентских запросов.
- Разные команды не могут независимо выпускать изменения в отдельных доменах.

## Рассмотренные варианты

### 1. Оставить монолит и оптимизировать его

Вариант предполагает сохранить текущий Java Spring Boot монолит и улучшать его через рефакторинг, индексы, кэширование, модульность и тесты.

Плюсы:

- Минимальная краткосрочная операционная сложность.
- Не появляются сетевые вызовы, Kafka и распределенная консистентность.
- Существующий процесс сборки и деплоя почти не меняется.

Минусы:

- Не решает независимое масштабирование бронирований.
- Не дает независимых релизов и четкого владения доменами.
- Оставляет общую базу данных долгосрочной точкой связанности.
- Откладывает миграцию, хотя бизнес уже выбрал постепенный переход.

### 2. Big Bang rewrite

Вариант предполагает переписать Hotelio как набор микросервисов и переключить трафик после полной готовности новой системы.

Плюсы:

- Можно сразу спроектировать чистую целевую архитектуру.
- Сервисы можно строить вокруг явных доменных границ.

Минусы:

- Очень высокий риск поставки и долгий период без бизнес-результата.
- Старое и новое приложение будут расходиться по поведению во время переписывания.
- Переключение трафика будет рискованным, потому что меняется сразу много компонентов.
- Нужно заново проверить все доменное поведение до получения реальной обратной связи.

### 3. Strangler Fig с постепенным выносом сервисов

Вариант предполагает поставить GraphQL BFF/Gateway перед монолитом и постепенно маршрутизировать отдельные сценарии во внешние сервисы. Монолит остается системой для доменов, которые еще не вынесены.

Плюсы:

- Миграционный риск снижается, потому что переносится один бизнес-сценарий за раз.
- Новую архитектуру можно проверять на ограниченном production-потоке.
- Legacy endpoints остаются доступными, пока сервисы дозревают.
- Извлеченные сервисы можно масштабировать и деплоить независимо.

Минусы:

- Промежуточная архитектура сложнее монолита: одновременно живут Gateway, монолит и новые сервисы.
- Нужны наблюдаемость, контроль роутинга, fallback и работа с консистентностью данных.
- На первом этапе часть доменных проверок все еще будет ходить обратно в монолит.

## Decision

Выбираем Strangler Fig с постепенным выносом сервисов.

Первым выносится создание бронирования в `booking-service`. GraphQL BFF/Gateway будет маршрутизировать создание бронирования во внешний `booking-service` по gRPC. На первом этапе `booking-service` будет обращаться к оставшимся доменам монолита по REST: проверка пользователя, отеля, промокода и доверия к отелю по отзывам.

После успешного создания бронирования `booking-service` сохраняет данные в собственной PostgreSQL базе и публикует событие `BookingCreated` в Kafka. `booking-history-service` читает эти события и поддерживает отдельное хранилище или таблицу для истории и статистики бронирований.

## Почему первым выносится BookingService

`BookingService` является лучшим первым кандидатом, потому что это бизнес-критичный и нагруженный сценарий с четкой границей: создать бронирование. Он уже является точкой оркестрации, поэтому его вынос сразу дает архитектурную ценность: критичный поток можно масштабировать, релизить и наблюдать отдельно.

При этом вынос остается управляемым: `UserService`, `HotelService`, `PromoCodeService` и `ReviewService` можно временно оставить в монолите и вызывать их по REST. Это позволяет не выносить все зависимости сразу, но уже проверить сервисную границу, gRPC, Kafka events и отдельную БД.

Создание бронирования также естественно порождает доменное событие `BookingCreated`, полезное для истории, статистики, аналитики, аудита и будущих уведомлений. Поэтому этот сценарий подходит для первого внедрения Kafka.

## Целевая промежуточная архитектура через 2 месяца

- Frontend обращается к GraphQL BFF/Gateway вместо прямой зависимости от всех REST endpoints монолита.
- Gateway реализует Strangler routing:
  - создание бронирования уходит во внешний `booking-service` по gRPC;
  - legacy reads и не перенесенные операции остаются в монолите.
- `booking-service` владеет логикой создания бронирования и собственной PostgreSQL базой.
- `booking-service` вызывает REST endpoints монолита для проверок пользователя, отеля, промокода и отзывов.
- `booking-service` публикует `BookingCreated` events в Kafka.
- `booking-history-service` потребляет `BookingCreated` и пишет read model в отдельное PostgreSQL хранилище истории/статистики.
- Legacy монолит и его PostgreSQL остаются рабочими для пользователей, отелей, промокодов, отзывов и не перенесенной функциональности.

## Целевая архитектура через год

- GraphQL BFF/Gateway является стабильной входной точкой для клиентских приложений.
- Booking capabilities полностью принадлежат `booking-service`: создание, чтение, отмена и жизненный цикл бронирований, если они входят в продуктовый scope.
- История, статистика, отчетность и audit views обслуживаются `booking-history-service` на основе event-fed read models.
- Оставшиеся домены постепенно вынесены из монолита в независимые сервисы: user, hotel, promo, review.
- Kafka используется для доменных событий между сервисами, а синхронные вызовы остаются только там, где нужен немедленный ответ в рамках пользовательского запроса.
- Каждый сервис владеет своей базой данных. Прямой доступ к БД другого сервиса запрещен.
- Монолит сокращен до тонкого compatibility layer или полностью выведен из эксплуатации после миграции критичных возможностей.

## План миграции по шагам

1. Поставить GraphQL BFF/Gateway перед монолитом и направить клиентские операции через него.
2. Описать gRPC контракт `booking-service` для создания бронирования.
3. Реализовать `booking-service` с отдельной PostgreSQL базой и схемой бронирований.
4. Перенести оркестрацию создания бронирования из монолита в `booking-service`.
5. Заменить внутрипроцессные зависимости REST-вызовами из `booking-service` в монолит для users, hotels, promos и reviews.
6. Добавить публикацию `BookingCreated` в Kafka после успешной записи бронирования.
7. Реализовать `booking-history-service` как Kafka consumer с отдельной таблицей или БД для истории/статистики.
8. Настроить Strangler routing в Gateway: создание бронирования идет в `booking-service`, остальные операции остаются в монолите.
9. Добавить observability: correlation IDs, structured logs, metrics, traces и dashboards для gateway, `booking-service`, Kafka и legacy-вызовов.
10. Провести contract, integration и rollback tests, затем постепенно переключать трафик через feature flags или route weights.
11. После стабилизации перенести чтение бронирований и затем извлекать остальные домены по приоритету.

## Риски и способы снижения рисков

- Отказы при сетевом взаимодействии `booking-service` с REST-зависимостями монолита.
  Снижение: timeouts, ограниченные retries, circuit breakers, понятный error mapping и fallback там, где это безопасно для бизнеса.
- Неконсистентность между booking DB, Kafka и history read model.
  Снижение: transactional outbox или надежный паттерн публикации событий, idempotent consumers, event keys по booking ID и возможность replay.
- Дублирование бронирований при повторных запросах.
  Снижение: idempotency key на создание бронирования и unique constraints в booking DB.
- Рост latency из-за сетевых вызовов в legacy domains.
  Снижение: latency budgets, метрики зависимостей, кэширование безопасных read-only данных и оптимизация самых дорогих проверок.
- Ошибки роутинга в Gateway во время миграции.
  Снижение: feature flags, canary routing, route-level tests и быстрый rollback на монолит.
- Расхождение контрактов между монолитом и клиентами сервисов.
  Снижение: consumer-driven contract tests и версионирование API contracts.
- Рост операционной сложности из-за Kafka и новых баз данных.
  Снижение: минимальный набор topics на старте, runbooks, health checks, alerts и локальная docker-compose проверка.

## Последствия решения

Положительные последствия:

- Создание бронирований можно масштабировать и деплоить независимо.
- Команда получает постепенную миграцию с ранней обратной связью.
- В архитектуре появляются Gateway, service-owned data и domain events без переписывания всех доменов сразу.
- История и статистика бронирований становятся eventually consistent и отделяются от write path.

Негативные последствия:

- Промежуточное состояние содержит больше компонентов, чем монолит.
- Часть бизнес-логики временно будет распределена между монолитом и `booking-service`.
- Командам нужно управлять контрактами, observability и надежностью распределенной системы уже на первом шаге.

## Что остается в монолите на первом этапе

- `UserService` и пользовательские данные в PostgreSQL монолита.
- `HotelService` и данные отелей в PostgreSQL монолита.
- `PromoCodeService` и данные промокодов в PostgreSQL монолита.
- `ReviewService` и данные отзывов в PostgreSQL монолита.
- Legacy REST endpoints для чтения и не перенесенных сценариев.
- Любая функциональность чтения или администрирования бронирований, которая не переносится в первый этап.

## Какие сервисы появятся

- `booking-service`: владеет созданием бронирований, предоставляет gRPC API, хранит бронирования в отдельной PostgreSQL базе и публикует `BookingCreated` events.
- `booking-history-service`: читает booking events из Kafka и хранит историю/статистику в отдельной таблице или PostgreSQL базе, оптимизированной под чтение и отчеты.
- GraphQL BFF/Gateway: входная точка для frontend и слой Strangler routing. Он направляет создание бронирования в `booking-service`, а временные legacy routes оставляет на монолите.

## Как будет происходить взаимодействие

- Frontend -> GraphQL BFF/Gateway: GraphQL.
- Gateway -> `booking-service`: gRPC для создания бронирования.
- Gateway -> monolith: REST для legacy operations, которые еще не мигрировали.
- `booking-service` -> monolith: REST для проверок пользователя, отеля, промокода и отзывов на первом этапе.
- `booking-service` -> Kafka: publish `BookingCreated` events.
- `booking-history-service` <- Kafka: consume `BookingCreated` events и обновление history/statistics store.

## Разделение данных

- Монолит сохраняет PostgreSQL с legacy tables: `app_user`, `hotel`, `promo_code`, `review` и оставшиеся не мигрированные таблицы.
- `booking-service` получает отдельную PostgreSQL базу и владеет write model бронирований.
- `booking-history-service` получает отдельное хранилище или таблицу для истории и статистики, наполняемую из Kafka events.
- Сервисы не читают и не пишут напрямую в базы друг друга; взаимодействие идет через API и events.
